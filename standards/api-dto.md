# API와 DTO 계약

적용 범위: 외부에 드러나는 HTTP API와 계층 간 데이터 표현. **MUST** 기존 API 계약·프로젝트 규약을 먼저 읽고 호환성을 보존합니다. 이 문서는 모든 응답에 wrapper를 강제하거나 DTO 수를 정하지 않습니다. 메서드·상태 의미는 [HTTP Semantics (RFC 9110)](https://www.rfc-editor.org/rfc/rfc9110.html), 부분 변경의 PATCH는 [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html)를 참고합니다.

## API를 정할 때

| 항목 | 규칙과 선택 기준 | 짧은 예 |
| --- | --- | --- |
| URI·메서드 | **SHOULD** 자원을 드러내는 URI와 의도에 맞는 GET/POST/PUT/PATCH/DELETE를 고릅니다. 기존 계약이 다르면 호환성을 우선합니다. | 좋음: `GET /catalog-entries/{id}`는 조회. 나쁨: 조회에 부작용 있는 GET. |
| 상태·오류 | **MUST** 성공·입력 오류·없음·충돌·서버 실패를 계약상 구분합니다. 오류 본문의 코드·메시지·추적 ID·필드 오류 형식은 프로젝트에서 하나를 선택합니다. | 좋음: 없는 ID에 명확한 상태와 오류 코드. 나쁨: 항상 200과 빈 객체. |
| 목록 | **SHOULD** 정렬·페이지 크기·다음 페이지 방식·동점 순서를 명시합니다. 작은 고정 목록은 페이지가 불필요할 수 있습니다. | 좋음: `createdAt`과 ID의 안정된 순서. 나쁨: 순서가 매번 달라 중복 항목 발생. |
| 재시도 | **MUST** 재시도될 수 있는 쓰기의 멱등성 조건을 정합니다. POST의 멱등성 키는 필요할 때만 도입하고 중복 요청의 응답·보존 기간을 정합니다. | 좋음: 같은 키의 중복 등록을 같은 결과로 처리. 나쁨: 타임아웃 재시도 때 두 건 생성. |
| 입력·호환성 | **MUST** 필수/선택, 누락/null/빈 값, 길이·범위·형식, 알 수 없는 필드 정책을 정의합니다. 공개 필드 삭제·의미 변경에는 호환 경로를 마련합니다. | 좋음: `title` 누락과 빈 문자열을 구분. 나쁨: 새 배포가 기존 필드를 몰래 삭제. |

## DTO를 만들 때

**SHOULD** 외부 계약이 내부 영속성 모델과 달라질 때 `CreateCatalogEntryRequest`, `CatalogEntryResponse`처럼 경계 DTO를 둡니다. 영속성 entity를 그대로 공개하면 내부 필드 노출, 지연 로딩, 스키마 변경의 전파가 생길 수 있습니다. 작은 내부 도구에서는 직접 사용을 선택할 수 있지만 노출 필드와 호환 위험을 확인합니다. `Command`는 여러 입력 경계를 한 작업으로 모으거나 작업 입력을 명확히 할 때만 사용합니다. 단순 전달을 위해 같은 필드의 DTO를 계층마다 복제하지 않습니다.

**MUST** DTO의 필수/선택/null과 검증 위치를 계약에 맞춥니다. 입력 형식 검증은 입력 경계, 비즈니스 불변식은 해당 정책에 둡니다. 요청 DTO → 작업 입력·domain 변환은 경계 또는 application에서 한눈에 찾을 수 있게 하고, 응답 조립은 presentation 경계에서 책임집니다. 이름과 패키지는 선택한 [언어](../README.md)·[프레임워크](../profiles/frameworks/) 프로필을 따릅니다. Java `record` 등 불변 전달 타입은 사용 중인 버전·직렬화 도구와 맞을 때 **MAY** 선택합니다.

“원본 전체 보존”이 계약이면 일부 필드만 가진 DTO로 조용히 축소하지 않습니다. 알려지지 않은 필드를 보존·거부·무시할지와 재직렬화 시 손실 가능성을 정하고 실제 샘플로 검증합니다. 동시에 외부 공개가 허용되지 않은 필드는 경계에서 제외합니다. 좋음: 원본 보존 범위와 공개 응답 범위를 각각 명시. 나쁨: 모르는 필드를 버리고 전체를 저장했다고 보고.

사람의 읽기 순서: 라우트·Controller → Request DTO와 검증 → 작업 입력·domain → 저장/외부 어댑터 → Response DTO·오류 매핑 → 계약 테스트. 실제 엔드포인트의 변경 이유와 미검증 항목은 [에이전트 결과](../agents/implementation.md)에 남깁니다.
