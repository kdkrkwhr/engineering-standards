# 구조 선택 가이드

**MUST** 요구사항과 현재 코드의 의존 관계를 먼저 살펴보고 구조를 선택합니다. 계층과 기능 중심은 서로 배타적이지 않습니다. Spring Boot의 새 프로젝트 기본 네 계층은 [별도 프로필](../profiles/frameworks/spring-boot.md)에 둡니다.

| 조건 | 시작 선택 | 커질 때 확인할 신호 |
| --- | --- | --- |
| 작은 CRUD, 적은 규칙, 한두 명 | 단순한 계층 흐름과 최소 패키지. 기능 폴더는 탐색에 도움 될 때만. | 핸들러에 규칙이 쌓이거나 기능별 변경 파일이 흩어짐. |
| 독립 기능이 여러 개, 팀이 나뉨 | 기능별 묶음 안에서 필요한 계층을 나눔. | 기능 간 직접 참조와 순환 의존이 늘어남. |
| 복잡한 불변식·상태 전이 | 도메인 정책을 분리하고 의존 방향을 명확히 함. | 규칙 중복, 인프라 교체·경계 테스트가 어려움. |
| 외부 시스템이 많거나 교체 가능성 높음 | 필요한 외부 경계에만 포트·어댑터를 둠. | 같은 계약의 구현이 실제로 여러 개이거나 통합 실패가 잦음. |

작은 일반 프로젝트의 시작 예시는 아래 정도면 충분합니다. `catalog`는 새로 만든 가상 도메인입니다.

```text
src/
  catalog/
    api            # 입력·출력 경계
    service        # 작업 순서와 정책 호출
    repository     # 실제 저장 경계가 있을 때
tests/
  catalog/
```

**SHOULD** 변경 이유가 생길 때만 파일과 경계를 더 나눕니다. 도메인 규칙이 독립적으로 복잡해지면 정책을 분리하고, 외부 의존을 바꿀 가능성이 실제로 생기면 인터페이스를 고려합니다. 작은 CRUD에 DDD 용어, 육각형 구조, 모든 클래스의 인터페이스를 일괄 도입하지 않습니다.

좋음: 한 기능이 커져 `catalog` 안에서 요청 처리·규칙·저장을 분리. 나쁨: 빈 `port`, `adapter`, `factory`를 미리 만들거나 모든 기능을 거대한 `service` 한 폴더에 모음.

예외: 프레임워크의 탐색 규칙, 기존 코드와의 일관성, 배포 단위, 명시적 프로젝트 계약이 다른 구조를 요구할 수 있습니다. 이때 현재 구조의 비용과 변경 시점을 [프로젝트 적용 문서](../templates/project-profile.md)에 짧게 적습니다.
