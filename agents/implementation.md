# 에이전트 구현 지침

이 문서는 프로젝트가 명시적으로 채택했을 때 적용합니다. 최신 사용자 지시와 작업 단계 제어, 프로젝트 계약·기존 컨벤션을 먼저 따릅니다. 형식적인 설계 승인 절차를 추가하지 않습니다.

## 일을 받았을 때

**MUST** 요청한 범위·입력·출력·오류·검증 기준을 읽고, 확인되지 않은 것은 `가정`으로 표시합니다. 요구를 임의로 추가·삭제하지 않습니다. `API 키가 있다`, `인증은 필요 없다`처럼 근거 없는 조건을 만들지 않습니다. 외부 API는 공식 스키마나 실제 응답 형태를 먼저 확인하고, 아직 확인하지 못했으면 구현·검증 한계로 남깁니다.

요구 → 구현 → 검증의 연결을 유지합니다. 여러 수용 조건이 있으면 아래 추적표를 쓰고, 사소한 변경은 같은 내용을 몇 줄로 적어도 됩니다.

| 요구·수용 조건 | 구현 위치 | 검증 방법 | 결과 |
| --- | --- | --- | --- |
| 예: 항목이 없으면 명확한 실패 | `catalog` 입력 경계·조회 작업 | 없는 ID로 경계 호출 | 미실행 / 실패 / 통과 중 하나 |

**MUST** “전체 객체를 보존” 같은 요구를 근거 없이 일부 필드 DTO로 축소하지 않습니다. 반대로 공개 응답에 비밀 필드를 무심코 포함하지도 않습니다. 어떤 필드를 보존·변환·제외하는지 [API·DTO 계약](../standards/api-dto.md)과 테스트로 확인합니다. DB를 쓰면 대상 DB·버전·격리 수준과 실제 동시성 검증 상태를 [트랜잭션 가이드](../standards/transactions.md)에 따라 확인합니다.

## 구현과 검증

1. **MUST** 기존 코드의 진입점, 처리, 저장·외부 연동 흐름을 찾아 변경 범위를 정합니다. 관련 없는 구조 변경은 피합니다.
2. **SHOULD** 책임이 바뀌는 지점에만 모듈을 나눕니다. 이름은 [명명 규칙](../standards/naming.md)과 선택 프로필을 따릅니다.
3. **MUST** 요구사항에서 독립적으로 만든 fixture와 기대값으로 테스트합니다. 구현 알고리즘을 테스트에 복사하지 않습니다.
4. **MUST** 외부 API·DB·인증처럼 실제 결과가 중요한 경계는 가능한 환경에서 통합 검증합니다. 모형 테스트만 수행했다면 이를 통합 통과로 적지 않습니다.
5. **MUST** 각 검증을 `통과`, `실패`, `미실행`으로 구분하고 실행 명령·환경·핵심 결과를 남깁니다. 실패를 숨기지 않습니다.
6. **MUST** 커밋할 때 작업 범위의 경로만 명시적으로 스테이징하고 staged 파일 목록과 diff를 검토합니다. `git add .`로 모든 변경을 무심코 포함하지 않습니다. 선택한 위생 검사가 있으면 staged index에 실행하고 탐지 한계를 보고합니다.

좋음: 스키마를 확인한 뒤 실제 응답의 선택 필드 누락도 검증. 나쁨: 임의 JSON으로만 테스트하고 “API 연동 완료”라고 보고.

## 사람에게 남기는 최소 결과

- **코드맵:** 요청이 들어오는 파일/함수 → 처리·정책 → 저장 또는 외부 호출 → 응답이 나오는 위치. 바뀐 파일의 역할을 한 줄씩 설명합니다.
- **변경 이유:** 요구와 설계 선택의 연결, 남긴 가정과 예외, 사람의 판단이 필요한 부분.
- **실행 결과:** 테스트·빌드·실제 통합 각각의 명령과 `통과/실패/미실행`, 미검증 이유.

프로젝트별 입력·출력과 적용 규칙은 [프로젝트 적용 문서](../templates/project-profile.md)에 기록할 수 있습니다. 실제 작업 지시는 그 문서보다 구체적인 최신 요구를 포함할 수 있습니다.
