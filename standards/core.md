# 공통 개발 원칙

언어·프레임워크에 관계없이 선택하는 기본값입니다. 기존 코드 관례, 프로젝트 계약, 최신 명시 요구가 있으면 [README의 우선순위](../README.md)에 따릅니다.

| 주제 | 규칙 | 이유와 짧은 예 |
| --- | --- | --- |
| 요구사항 | **MUST** 요구와 수용 조건을 확인하고 그 범위만 구현합니다. 요구를 임의로 추가·삭제하지 않습니다. | 좋음: “목록은 제목 순”을 테스트와 연결. 나쁨: 요청 없는 인증 단계를 추가. |
| 책임 | **SHOULD** 한 모듈에는 한 응집된 책임을 두고, 의존 방향과 외부 경계를 설명할 수 있게 합니다. | 좋음: 가격 계산을 한 정책에 모음. 나쁨: 웹 핸들러가 DB·계산·응답 조립을 모두 담당. |
| 오류 | **MUST** 예상 가능한 실패를 구분하고 경계에서 사용자가 이해할 수 있는 결과로 바꿉니다. 오류를 성공처럼 숨기거나 비밀값을 로그에 남기지 않습니다. | 좋음: 없는 항목을 명확한 실패로 반환. 나쁨: 모든 예외를 잡아 빈 목록 반환. |
| 명명·용어 | **MUST** 같은 개념에는 같은 이름을 씁니다. 단위·단복수·상태를 이름 또는 타입으로 드러냅니다. | 좋음: `timeoutSeconds`. 나쁨: 단위를 모르는 `timeout`. [세부 규칙](naming.md). |
| 테스트 | **MUST** 요구사항과 독립적으로 만든 입력·기대값으로 중요한 동작과 경계를 검증합니다. 테스트가 구현 수식이나 분기를 그대로 베끼지 않게 합니다. | 좋음: 명세의 예시 결과를 고정 fixture로 확인. 나쁨: 구현 함수를 테스트의 기대값 계산에 재사용. |
| 변경 범위 | **MUST** 요청 범위 밖의 리팩터링·설정 변경은 분리하거나 근거를 기록합니다. 기존 코드 관례를 우선합니다. | 좋음: 수정한 API 주변만 정리. 나쁨: 작은 버그 수정에 전체 패키지 이동. |
| 문서·리뷰 | **SHOULD** 구조·대안·예외의 이유와 검증 결과를 사람이 재현할 수 있게 남깁니다. | 좋음: “이 경계는 외부 API 교체를 위해 분리”라고 기록. 나쁨: 이유 없이 추상화만 추가. |

실제 통합 경계가 있는 경우 **SHOULD** 그 경계를 실행해 확인합니다. 외부 API, DB, 인증, 파일 시스템의 모형 테스트만 통과했다면 통합 검증을 **미실행**으로 표시합니다. 위험이 낮은 순수 함수 변경은 독립 단위 테스트로 충분할 수 있습니다.

예외: 언어 관용구, 생성 코드, 외부 계약, 기존 공개 API 호환성 때문에 표현이 달라질 수 있습니다. 예외는 프로젝트의 [적용 문서](../templates/project-profile.md)에 범위와 이유를 기록합니다.
